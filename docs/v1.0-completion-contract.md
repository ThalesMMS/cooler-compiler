# Cooler v1.0.0 completion contract

This versioned contract defines the finite meaning of “100% complete” for
Cooler v1.0.0. The contract has been satisfied and
[Cooler v1.0.0](https://github.com/ThalesMMS/cooler-compiler/releases/tag/v1.0.0)
was publicly released on September 2, 2026.

## Release identity

- Private release candidate:
  `e18373d9f8ebc5117a9451c871759f0c09580453`.
- Public source commit:
  `07f68ab0600a6d61ef51f9160f3bc007149288ed`.
- Annotated public tag: `v1.0.0`.
- Sanitized source mapping: 439 published files matched the candidate export by
  path and SHA-256.
- Published release assets: four target archives, `release-manifest.json`, and
  `SHA256SUMS`.
- Post-upload verification: all six downloaded assets matched the qualified
  local files byte-for-byte.

The authoritative package hashes and platform qualification boundaries are in
the [v1.0.0 validation ledger](release-validation-v1.0.0.md).

## Locked product scope

Cooler v1.0.0 includes:

- the classic COOL lexer, parser, static semantics, runtime, built-ins, and
  deterministic 32-bit `Int` behavior described by the
  [language contract](cool-language.md);
- ordered multifile `SourceUnit` compilation, typed AST, symbols, stack IR,
  CFG, pseudo-assembly, bytecode verification, and optional verified
  educational optimization;
- bounded deterministic compiler and VM sessions, interactive input,
  source-level and reverse debugging, breakpoints, watches, logpoints, heap
  inspection, and relationship visualizations;
- the CLI, local browser and native GUIs, reports, exports, versioned schemas,
  stable public Go API, and local COOL LSP; and
- rule-level conformance, local differential testing, fuzz/property/session
  infrastructure, benchmarks, reproducible packaging, checksums, provenance,
  and explicitly bounded target evidence.

The normative details remain in the linked interface and language documents.
This contract freezes their integrated v1.0.0 boundary; it does not replace
those documents.

## Intentional non-goals

The release does not promise:

- MIPS/SPIM output or reference-runtime ABI compatibility;
- modules, imports, separate object files, or linking;
- native machine-code generation;
- byte-identical reference diagnostic wording;
- a hosted or multi-user compiler/debugger/LSP service;
- hosted fuzzing, hosted benchmarks, GitHub Actions, hosted CI, or CI badges.

These are explicit product boundaries, not exceptions for missing classic COOL
language behavior.

## Completion states

The project tracked four separate completion states. All are complete for
v1.0.0, with the evidence limits stated below:

- **Implemented:** the required source, tests, fixtures, schemas, documentation,
  and user-facing interfaces exist in the released source tree.
- **Locally verified:** the candidate received the recorded bounded local
  module, build, export, packaging, Windows, API, and LSP checks. The complete
  conformance/differential evidence was established during the immediately
  preceding stabilization sequence; extended campaigns were not rerun after the
  final public-safe example-catalog adjustment and are not represented as such.
- **Artifact-qualified:** two complete builds produced six byte-identical release
  files. Windows amd64 additionally passed bounded packaged CLI, LSP,
  browser-GUI, and native WebView2 execution. Linux amd64/arm64 and macOS arm64
  were reproducibly cross-built and checksum-qualified; runtime execution on
  those targets is not claimed.
- **Publicly released:** the exact sanitized tree, annotated tag, manifest,
  checksum file, and already-qualified archives are public. Post-upload download
  comparison, clean-clone builds, and external Go module resolution passed.

“Complete” in this contract therefore means complete within the declared
educational scope and the explicitly recorded bounded verification policy. It
does not mean universal runtime certification on every architecture.

## Completed sequential main-only protocol

The final stabilization sequence was implemented sequentially on the private
`main` branch without implementation pull requests. Each step was closed with
its commit and evidence before the next step advanced. Candidate changes
invalidated dependent package identities and produced a new final candidate,
which is the identity recorded above.

## Maintenance after v1.0.0

Future accepted work is an enhancement beyond v1.0.0, not unfinished work
required to make this release complete. A maintenance release may correct
documentation or defects without rewriting the historical `v1.0.0` tag. New
feature scope should be introduced through a new roadmap milestone and preserve
the stable CLI, schema, diagnostic, archive, and public Go API compatibility
policies.

The [roadmap](../ROADMAP.md) records released and exploratory directions, the
[contributing guide](../CONTRIBUTING.md) defines the development workflow, and
the [development/publication contract](development-publication.md) defines the
one-way public export process.
