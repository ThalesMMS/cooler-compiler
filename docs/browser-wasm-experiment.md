# Browser Go/Wasm experiment (#85)

The existing Go compiler and educational VM run inside a browser Worker through
the public compiler facade. A static page sends local `postMessage` requests;
there are no compile/run HTTP endpoints and no Go backend process. This ports
the existing implementation to `js/wasm`; it does not emit Wasm from COOL IR.

## Reproduce locally

With the repository's Go toolchain and Node installed:

```sh
node scripts/build-wasm.mjs
node scripts/serve-wasm.mjs
```

Open `http://127.0.0.1:9092`. Compile and run the example, or enter a program
using `in_string()` to exercise requested input. **Compare native fixtures**
compares nine cases with results generated by the same adapter on the native VM:
signed int32 overflow, dynamic/static dispatch, `SELF_TYPE`, semantic/runtime
errors, instruction budget, interactive input and an ordered multifile project.
Comparison includes diagnostic spans and full retained runtime projections
(output, steps, stack, frames and trace), excluding host memory/timing metadata.

The build creates `dist/browser-wasm` with the Wasm binary, HTML/JS, native
fixture JSON, build metadata and Go runtime license. Copy the complete directory
to another static server with `.wasm` served as `application/wasm`. The included
Node server binds only loopback and serves an explicit asset allowlist using
GET; it does no compilation or VM execution. Opening the page as `file://` is
not supported because Worker and fetch loading need an HTTP origin.

`wasm_exec.js` is copied from **the same GOROOT** used to build the binary;
do not mix runtime/toolchain versions. This follows the [official Go Wasm
instructions](https://go.dev/wiki/WebAssembly). Assets are local, with no CDN,
package install, hosted API or browser extension. The build metadata records
toolchain, base commit, dirty-worktree state, bytes and SHA-256. Native fixture
generation is a build-time command, not a backend service.

## Protocol and limits

`internal/wasmbridge` is experimental and not a supported public API. Its JSON
adapter accepts a request ID and `compile`, `run`, `input` or `dispose` action.
Compile accepts ordered in-memory `SourceUnit` objects and preloaded input;
run accepts a step budget; input requires the current request sequence and a
line. Every compile disposes the previous session. No filesystem paths are
opened by this adapter. The prototype editor exposes one source, while its
protocol and comparison corpus exercise multiple sources.

Bounds: 128 KiB request JSON, 1–8 sources totaling 64 KiB, 16 KiB input/output/
strings, 1,000 object allocations, 128 call frames, 64 retained trace entries /
1 MiB, 10,000 instructions per run and 100,000 total per compiled session.
The existing facade validates source identity, input sequences and VM policy.
This does not impose an independent hard cap on Wasm linear memory.

Go execution can occupy the Worker's event loop, so cancellation is performed
by the **main thread terminating the Worker**, not by waiting for a cancellation
message to execute inside Go. The main thread also enforces an 8-second startup
watchdog and 5-second operation watchdog. A timeout stops the runtime; use
**Cancel and restart** to recreate it. Source remains in the editor; runtime,
input events, heap and execution history are discarded. Requests from previous
Worker generations are ignored, and pending callers reject. Calls after a
stopped Worker reject immediately. This is restart-based cancellation, not
resumable cancellation of a partially executed operation.

## Measured local observations

Windows/amd64, Go 1.26.4, Codex in-app Chromium reporting Chrome 152.0.0.0:

| Measurement | Observed value |
| --- | ---: |
| Stripped Wasm binary | 5,447,663 bytes |
| Offline gzip estimate | 1,485,620 bytes |
| Initial fetch + instantiation + Go startup | 28.2 ms |
| Subsequent page reload startup | 20.8 ms |
| First Hello compilation in Worker / round trip | 82.8 / 83.1 ms |
| First Hello execution in Worker / round trip | 14.6 / 16.8 ms |
| Interface animation frames during first compile / run | 4 / 1 |
| Go heap after first compile | 3,856,616 bytes |
| Go system accounting after first compile | 7,143,424 bytes |
| Wasm linear memory after first compile | 10,485,760 bytes |
| Linear memory observed during corpus comparison | 12,058,624 bytes |

The local server sends the uncompressed Wasm; gzip size is a build-time estimate,
not measured transfer compression. Startup includes local fetch and may benefit
from OS/browser caches. Go heap/system and Wasm linear memory are overlapping
measurements, not additive or browser-process resident memory. They are endpoint
observations, not peak memory claims. Each page request records Worker latency,
round trip, memory and interface frames, tagged with the Worker generation.
The live view retains the latest 32 operations. These small observations do not
justify a near-native performance promise or browser-wide support claim.

## Validation and decision

Actual browser validation compiled and printed `Hello from WebAssembly!`,
matched **9/9 native fixtures**, suspended for input and printed the supplied
`browser input`, and cancelled/restarted a 10,000-step loop while preserving
its source and clearing the VM. Interface frames continued during compilation.
The native fixture executable was not running as a service during these checks.

```sh
go test ./internal/wasmbridge
node --test experiments/browser-wasm/client.test.mjs
```

The short full native Go suite and vet passed; pinned lint passed after cleanup.
Bridge tests also executed as `js/wasm` under Go's Node runner. Client tests cover
pending cancellation, stale replies, startup/operation timeouts and calls after
failure. Independent review identified the post-stop request gap now fixed.
Safari, Firefox, standalone Chrome/Edge and native macOS WebView were unavailable
for validation; only the browser identified above was exercised.

Keep this as a reproducible experiment. The desktop GUI, HTTP API, filesystem
loading, LSP, watches, heap browser, reverse-debugging controls, report exports
and persistent drafts are not integrated into this page. The underlying Go VM
remains shared, but full product replacement requires further browser testing,
memory profiling, asset caching/versioning and UI integration.
